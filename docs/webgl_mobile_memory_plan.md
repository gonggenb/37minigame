# iPhone Safari WebGL 关卡加载内存优化方案

日期：2026-09-10。状态：第一、二批的纹理压缩、渲染配置、轻量首页与卸载顺序已实施；Play Mode 通过 60 项检查。实现与构建证据见 [验证报告](validation/webgl_mobile/README.md)。尚未通过 iPhone 真机验收；下面的基线表保留实施前状态。

## 1. 结论与证据边界

用户在 iPhone 13 Pro Safari 遇到“因为出现错误重新加载”。这与网页进程异常一致，内存峰值是优先验证的假设；尚无设备崩溃日志，不能排除 GPU/驱动或其他运行异常。

上一轮线上桌面浏览器已进入首页。这不能替代 iPhone Safari 验证。本轮检查本地源码、场景 YAML、导入设置与本地 WebGL 构建；没有确认线上 latest 与本地文件哈希一致。

需要分别测量：下载/解压缓存、Unity WebAssembly 堆、纹理与渲染缓冲、浏览器音频与其他页面开销。不能把包体大小当成峰值内存，也不能把不同统计口径直接相加。全项目文件夹大小不等于发布包大小；没有打入构建的源文件不列为减包收益。

## 2. 当前项目的具体问题

| 项目 | 检查所得 | 含义与限制 |
| --- | --- | --- |
| 启动场景 | `ProjectSettings/EditorBuildSettings.asset` 首场景为 `MainPrototype` | 目前打开首页就进入第二关完整场景，而非独立轻量首页；场景直接引用的依赖已进入加载范围。 |

| 第二关直接图片引用 | 场景直接引用 91 个唯一 PNG，其中 83 个默认 `textureCompression=0`；扫描到的 PNG WebGL override 未启用 | 有明确的纹理压缩空间。仅直接引用统计，未展开 Prefab/模型的全部传递依赖，也不包含所有运行时 Resources 加载。 |
| 纹理量级 | 上述 83 张按源尺寸、默认最大尺寸、RGBA32 基础层估算约 105.36 MiB | 仅理论量级，非 Unity 导入后统计或 Safari 实测；不含 mip、CPU 副本、对齐与其他资源，最终要确认实际 texture format。 |
| 单个例子 | `spr_treasure_chest_closed_v01.png` 为 1254×1254，默认关闭压缩 | RGBA32 基础层约 6 MiB；256×256 同格式为 0.25 MiB，前提是实际显示尺寸允许。 |
| 场景资源引用 | `BattleScreenController` 直接挂载多张战斗背景、多组敌人与 Boss 动画；第二关直接引用 15 个 WAV | 不等到第一次战斗才开始建立全部资源依赖。音频引用数量不代表全部已解码。 |
| 主角动画缓存 | `HeroDirectionalArt` 首次访问加载八方向跑步/待机；`HeroAttackArt` 首次访问加载四种攻击 | 共用资源值得保留，但首次同步加载有集中成本；优先在关卡准备期间完成，再评估是否需要拆小。 |
| 洞穴缓存 | `CaveRoomController` 已按主题、横竖屏按需加载，但字典没有容量/退出清理策略 | 已有延迟加载基础；游玩多个洞穴或旋转手机后，已加载背景可能在本场景累计。 |
| 音乐 | 首页和主地图音乐已设置 Streaming、关闭预加载；`Awake` 仍加载钟声、Boss 转场声等 | “改成 Streaming”不是新增优化。需核查 Unity 6.5 Web 音频实际支持、解码时机、浏览器内存和相位切换。 |
| 移动渲染 | WebGL 默认画质 High；模板未限制 `devicePixelRatio` | 有降低 GPU 负担的空间，但不能替代资源与加载流程优化。 |

## 3. 第一批：小范围减重，并建立对比数据

### A. WebGL 手机资源档

- 新增可重复执行的 WebGL 手机构建配置/编辑器工具，明确纹理格式、分辨率、画质与诊断开关；避免只在某台机器的 Library 设置里改变格式。
- iPhone 测试包优先验证 ASTC。透明角色先试 ASTC 6×6，照片式背景先试 8×8；以实际透明边缘、像素轮廓和文字清晰度决定是否接受。
- 保留原始 PNG 和高精度美术，只改目标平台导入档。宝箱等小型显示物件优先降到 256/512；大背景按真实显示需求评估 1024/1536；角色动画不能整库机械缩小，须验证每帧切片、脚点、攻击轮廓。
- 保留不需要 CPU 读取的资源 `Read/Write=false`；本轮扫描的 PNG 已关闭，不能把这一项重复计为新增收益。纯 UI 图片评估禁用 mip，3D 地表保留必要 mip。
- 在浏览器中确认实际纹理扩展和是否发生软件解压。若需要兼容不支持 ASTC 的设备，评估 ETC2 或独立兼容构建；不要让全部终端无条件加载仅面向 iPhone 的包。
- 手机先使用 DPR 上限 1.5 的对比档，配合降低阴影和质量；DPR=1 作为诊断档。DPR 从 3 降到 1.5 时像素数变为四分之一，但整页内存不会同比下降。

### B. 场景引用减负

- 用 Unity `AssetDatabase.GetDependencies` 和 BuildReport 列出每关实际依赖与构建占用，定位不属于该关的敌人、Boss、旧背景和音轨。
- 教学只挂教学所需资源；第三关、中期 Boss 等各自配置。检查第二、三关均引用中期 Boss 音乐是否确实需要。
- 去掉实际已不用的场景序列化引用；仅隐藏 GameObject 不会解除资源引用。
- 整理资源生产菜单，避免下一次重建场景又把全量资源挂回去。
- 共用主角/常用敌人预先在关卡准备阶段加载，避免首次碰怪时同步加载卡顿。普通战斗仍继续主时间，不能用新增暂停掩盖加载问题。

这批主要改导入设置、配置和引用；画面风险是压缩伪影与分辨率降低，需做 540×960 和 960×540 比较。没有真机基线前，不承诺固定节省百分比。

## 4. 第二批：轻量首页与先卸旧关再载新关

这是针对启动和切关峰值的核心调整，建议与第一批一起作为本轮优化范围。

新增轻量 `BootMenu` 场景，只负责 Logo、首页、选关、存档读取和共享 UI。把首页所需逻辑从 `PrototypeHUDController` / `GameFlowController` 中最小拆出，避免新首页间接引用战斗/地图整套依赖。沿用现有布局、素材方向、RuntimeChineseFont 与文案目录。

目标流程：

```text
打开网页 → 轻量首页 → 选择关卡 → 加载页
加载页 → 释放旧关引用 → 卸载旧关 → 清理不再使用的资源
       → 加载目标关 → 初始化本关必需资源 → 确认可操作 → 开始计时
```

- 保留一个轻量常驻场景/过渡场景，避免试图卸载最后一个场景。加载界面和跨关意图留在轻量层。
- 必须在开始加载大场景之前完成旧关卸载。不能先挂起 `allowSceneActivation=false` 再排队卸载旧关，因为异步队列可能被阻塞。
- 旧场景移除后，先清理相应缓存/音频引用，再在过渡页等待 `Resources.UnloadUnusedAssets()`；有引用的对象不会因为调用清理接口就自动释放。
- 原有“至少 5 秒加载页”可以保留，但用真实时间统计，不能通过保留旧场景来凑时长。新场景即使已初始化，也必须在过渡结束和起手选择完成前保持不可操作、不扣主时间。
- 保留教学解锁、下一关自动开局、失败回首页、第三关解锁、Logo 每次应用仅播一次。载入失败时回到可交互的轻量首页，恢复正确的时间与输入状态；不留下黑屏。
- 清理仅发生在关卡切换等安全时机。不要在每次普通战斗结束调用全局 GC；小型共用资源可以继续缓存。
- WebAssembly 堆扩容后一般不会因此缩小已预留的堆；这里的收益是减少同时存活对象和后续扩容需求，浏览器进程占用不一定立即回落。

注意：仅拆首页和异步场景不等于减少首次 `.data` 下载；内置全部场景和 Resources 仍可能包含在启动包中。若包数据本身仍构成主要压力，执行第四批。

## 5. 第三批：音频与缓存的生命周期

- 首先在同一设备比较正常音频包与完全不加载长音乐的诊断包；仅将音量设为 0 不能用于排除音频内存。
- 按首页/探索/洞穴/Boss 分组加载，转场后停止 AudioSource 并解除引用，在安全时机卸载不再使用的数据；确认当前 Unity Web 支持及实际释放效果。
- 60 秒、44.1 kHz、双声道音频若全部解码为 float PCM，基础样本约 20.2 MiB。该数字只是量级示例，不意味着现有每条音轨都已完整解码。
- 保留音乐风格；优先缩短可无缝循环段、合理降低采样率，对非必要立体声效果评估单声道。降低压缩码率主要改善下载，不保证同比减少解码内存。
- 洞穴只缓存当前/必要近期主题与方向；旋转后安全替换，退出时按预算释放，不破坏仍在绘制的共享纹理。
- 武学图标 RenderTexture 缓存已有 `ClearCache`，将其纳入换关生命周期；不要重复释放仍在使用的 GPU 对象。
- 主角动画是高频共享资源，先压缩再考虑释放；避免为了少量缓存空间造成每次战斗重新加载。

## 6. 第四批：仍有需要时，拆分下载包

把共用基础资源、教学、第二关、第三关、Boss/洞穴扩展拆成独立 AssetBundle 或 Addressables 内容包，按需下载、加载、释放。共用纹理和字体只保留一份；从场景直连引用与 Resources 中移出的资源才能真正离开启动依赖。

- Web 资源包使用平台支持的压缩路径，评估 LZ4；不能直接套用桌面 LZMA 加载方案。
- 先验证 Unity Play 对额外文件、相对 URL、响应头、缓存与跨域的实际支持，再决定是否继续使用该站点或改发布结构。
- 不在同一次改动中直接迁移全部资源。先用一个关卡验证下载、失败重试、释放和重复进入，再扩展。
- 第四批会增加资源版本与加载失败处理成本，应由第一至三批真机测量决定是否实施。
- 缩短 JS/gzip 下载文件、提高内存上限、延长加载动画，都不能单独替代这些运行时优化。

## 7. 测量与验收

先建立当前包基线，保存包标识、iOS/Safari 版本、设备、屏幕方向、缓存冷/热状态与是否运行在 Unity Play iframe 中。

关键采样点：网页开始、包解压结束、首页稳定、切关前、旧关卸载后、新关加载峰值、关卡首帧、首次战斗、首次洞穴、Boss、返回首页。

记录 Unity 总分配/预留、Wasm 堆、已加载 Texture2D 数量及估计占用、音频数据状态、渲染尺寸、阶段耗时和首个错误。Safari Web Inspector 与可获取的 iOS WebContent/GPU 终止记录用于判断网页进程问题；Unity Profiler 数字不代表整个 Safari 页面。

对比批次：基线 → 仅纹理/渲染 → 加首页与过渡改造 → 加音频/缓存。一次明确一组变量，避免无法判断是哪项有效。使用同一构建的独立页面与 Unity Play 嵌入页面对比，区分游戏与宿主页开销。

首轮验收条件：

1. iPhone 13 Pro Safari 冷启动、热启动各 5 次，无错误重新加载。
2. 教学 → 第二关 → 第三关 → 首页，连续 10 轮切换，无黑屏、死锁、音频重复和重新加载；首次加载及切关峰值低于基线。
3. 缓存预热后，相同路径的资源数量及占用不持续逐轮增长；预留堆不回落不单独判定为泄漏。
4. 横竖屏、字体、切片、透明边缘与首页交互通过检查；执行 `37 MiniGame/Validate Chinese Fonts`，构建不得绕过。
5. 普通战斗继续扣主时间；洞穴暂停；最终 Boss 独立计时；加载与起手选择期间不偷跑计时。

上述次数是本轮验收起点，不代表覆盖全部 iPhone 与 iOS。性能目标需按基线制定；不使用未经验证的“Safari 固定最大内存”作为保证。

## 8. 预计涉及文件与编辑器工作

首批拟修改：WebGL 模板、目标纹理 `.meta`、质量/构建配置、场景资源引用及对应 Builder。

第二批拟修改：`LevelLoadingScreen.cs`、`LevelSequence.cs`、`PrototypeHUDController.MainMenu.cs`、必要的 `GameFlowController` 入口、Build Settings；拟新增轻量首页场景与控制器、过渡控制和内存采样工具。

第三批拟修改：`MainMapMusicController.cs`、`CaveRoomController.cs`、动画/图标缓存管理及音频配置。

轻量首页、构建首场景、三个关卡入口和 UI 引用已由编辑器工具生成并验证，无需手动绑定。原始美术保留，目标纹理仅改变 WebGL 导入档；第三、四批音频与分包工作仍待真机结果决定。

本次只新增此方案文件，没有修改运行时代码、场景、资源、打包设置或线上发布。
